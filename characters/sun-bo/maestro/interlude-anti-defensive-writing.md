# 《总谱》Interlude 去防御性写作规范

> 适用范围：`characters/sun-bo/maestro/chapters/` 中所有行业 Interlude 的起草、润色和忠实度审查。本文是写作规范，不新增世界设定；若与 `lore.md`、`lore-maintenance.md` 或已经确定的正文事实冲突，以权威事实源为准。

## 一、写作目标与核心规则

Interlude 是**简短的架空 AI 技术编年史**，按一段时间内的重要公开模型进展组织，而不是单个模型的发布公告、公司人物戏或百科词条。重点交代：**何时、谁发布了什么、采用何种已确定的技术路线、实际达到什么能力和使用状态、相对此前改变了什么**。可以同段介绍多个厂商，按时间、技术变化和必要对照自然衔接；不强迫每家公司平均分配篇幅。

**去防御性的首要原则：先写发生了什么及其意义，不要在每个事实后面抢先解释它“并不意味着什么”。** 文风是平静、具体、有信息密度的科技纪实，不是给想象中的审稿人提交答辩，也不是营销文案。

本规范借鉴学术 anti-defensive writing 方法，但把“主张—证据—必要限定”的关系转为小说中的**“发布事实—可观察能力—产品状态—必要边界”**。提升表达力度不得改变 Canon，也不得靠虚构 benchmark、架构细节或竞争排名制造突破感。

## 二、事实优先级与必须保留的边界

正文中的表达精简服从以下优先级：

1. **已确定 Canon 与故事时间**：`lore.md` 里的型号、时间、技术能力、受邀测试/公开 Preview/正式发布/API 开放、第三方接入；`worldview.md` 与已写章节中的人物经历。
2. **技术与产品分层**：模型推断、API 参数、网页端（如 EpochChat）的产品调度、CLI Agent（如 Encoder、Kybernetes）的上下文检索/编辑/执行工具，各归其位。不能因为删掉限定就把模型写成能够自行操作本地电脑的成熟 Agent。
3. **重要的真实不确定性与代价**：尚未发布、仅邀测、缺少公共 API、较高推理延迟或成本、性能只在特定任务改善等。如果删除会改变读者对事件的理解，必须保留。
4. **文字的直接性、节奏与气质**：在前三项成立后，删除重复辩护、套话和无信息量的转折。

**保留必要限定一次，放在最能解释事实的位置。** 不要每介绍一项新能力就跟一句“但模型并非万能”；也不要为了精练而把“公开预览”删成“正式推出”，或把“部分编程任务表现优秀”改成“编程全面领先”。

### 三类限定的处理

| 类型 | 处理 | 例子 |
| --- | --- | --- |
| 决定事实是否成立的状态与范围 | 必须保留 | “官方平台公开预览，尚未开放公共 API” |
| 解释真实能力取舍的限制 | 就近、简短写一次 | “扩展思考提高了复杂任务表现，也增加了延迟和使用成本” |
| 只为提前阻止误读的免责声明 | 删除或改成正向事实 | “这不意味着它已经拥有真正智能，也不保证一切任务正确” |

## 三、重点清理的防御性写法

### 1. 不要反复使用“不是 X、并不意味着 Y”

以下句式不是禁词，但默认检查必要性：“当然，这并不意味着……”“需要强调的是……”“并不代表……”“尚不足以……”“不能简单认为……”“尽管取得进展，但仍然……”。

优先写正面、可检验的范围：

**防御式**：Atlas III-Nova 已有明显进步，但这并不意味着它能够胜任全部工程任务，更不能认为它已经具备完整自主 Agent 能力。

**建议式**：Atlas III-Nova 在长上下文和代码理解上进入一线竞争范围，仍主要通过官方平台处理开发者提交的任务。

如果自主执行边界在这篇 Interlude 中确实重要，另以一句说明执行仍由外部工具承担即可，不必把边界重复到每个厂商段落。

### 2. 不要叠加语气缓冲词

“可能、或许、一定程度上、相对而言、总体来说、可以说”连续出现时，先判断源事实是否已经确定；已确定的事实直接陈述，未确定的事实指出具体未知之处。

**防御式**：这次升级或许在一定程度上改善了部分较复杂的编程任务表现。

**建议式**：新版强化了多文件接口理解与复杂代码调试。

如 Lore 仅写“部分场景”，则要保留“在部分任务中”，不可扩张成普遍领先。

### 3. 不以免责声明开篇或收尾

开头直接落在时间窗口、模型和技术变化上。结尾可以指出竞争格局或下一轮技术方向，但不加“当然上述变化尚不意味着革命已经完成”式的自我撤回，也不以空泛的“未来仍充满不确定性”收束。

### 4. 不用自我贬低或营销口号替代事实

避免“不过只是一次初步尝试”“称不上真正的突破”等无依据贬低；同时避免“划时代”“震惊整个行业”“彻底颠覆”“全面碾压”等无依据夸大。若发生重要代际提升，直接写**新能力、前后差异、开放范围和真实代价**。

### 5. 不用重复的技术免责声明充字数

同篇中已经交代一次“外部应用负责执行工具”，其他模型除非存在不同的工具开放状态，就不再重复“不代表它能自主操作电脑”。正文不是 Lore 的安全注释汇编。

## 四、信息组织与篇幅

默认目标约 **300—600 个汉字**，可依据同期真正重要的进展伸缩；不为了凑齐全部厂商而塞进低重要性的版本。多厂商同篇时，可以采用连续的短段落，不必写产品卡片或每个模型的四项小标题。

建议行文顺序：

1. **时间与本期主要变化**：用一两句建立时间窗口。
2. **代表性的模型发布**：型号与发布/Preview 状态，突出相对于上一代的能力变化。
3. **必要对照**：通用推理、复杂编程、高效多模态、编辑器模型等路线有何不同；只比较 Lore 已确定的维度。
4. **简短收束**：市场中出现了哪些新的实际选择、成本或应用方式；不要替孙博宣布未来命运。

这是组织检查，不要求机械写成四段。信息量不足可更短。首次出现的必要技术术语可以顺势说明，不单列概念百科。不复述厂商整个创立历史，也不为体现“科技纪实”虚构内部会议或人物台词。

## 五、技术叙事的证据纪律

- **已确定才写成事实**：型号、发布时间范围、访问渠道、能力定位来自当前 `lore.md`；未定参数规模、Dense/MoE 结构、训练流程细节、精确 benchmark、价格和速率不得补造。
- **现实对标只作作者侧校准**：现实 GPT、Claude、Gemini 型号原则上不进入架空世界公开叙述。
- **模型能力不等于产品能力**：基础模型的推理与网页端应用（如 EpochChat）的自动调度属于不同层次；通过 API 使用的推理档位不必等同网页调度。CLI Agent（如 Encoder、Kybernetes）的多文件修改由基础模型加 Harness 的工作区上下文与执行工具共同完成。
- **明确发布状态**：内部研究、受邀测试、Public Preview、正式发布、API 开放、Agent 接入分别记录，不把“发表成果”写成“所有人已经可使用”。
- **重要负面事实照写**：高延迟、用量限制、仍存在误判、Preview 不稳定等若对定位有影响，应保留；但以具体能力取舍表达，不在每段末尾机械插入局限警语。
- **竞争评价有条件**：写“在部分代码任务进入一线竞争”，不写没有来源的总榜名次或“某模型永远胜过另一模型”。缺数据时不要编 benchmark 数字。
- **Interlude 的全知是行业视角，不是无约束预知未来**：可以概述同一时间窗口的已确定发布事件，但不能让尚未发生的结果成为当时公众已有的结论；其独立时间窗口应在标题或首段清楚呈现，且不把行业已知等同于孙博已知。

## 六、三组《总谱》专用改写示例（示范语气，不新增 Canon）

**示例 A｜能力边界不堆叠**

防御式：GRM-4.1 将通用能力和深度推理融合，但这并不意味着它已经能稳定处理任何复杂任务，当然也不代表它具备成熟 Agent 的全部功能。

精练式：GRM-4.1 将通用响应与更充分的推理结合，复杂代码和多步骤任务表现明显提升。EpochChat 根据任务难度调度不同的计算量。

**示例 B｜Preview 状态明确而不辩解**

防御式：虽然 Atlas III-Nova 还只是初期发布，没有完全开放公共 API，而且无法保证各个任务都比对手出色，但它仍然值得关注。

精练式：Atlas III-Nova 在长上下文理解与文字创作中进入一线竞争水平，首先通过 Aleph 官方平台开放体验。

**示例 C｜模型与 Harness 分层自然呈现**

防御式：GRM-4.1-Byte 的跨文件体验有所改善，不过必须指出这种改善并不全部来源于模型自身，而是部分来自终端 Agent 工具。

精练式：GRM-4.1-Byte 提升了多文件代码修改的指令遵循，Encoder 同步优化了工作区检索与差异应用机制，工程执行更加顺手。

示例用于展示删减方法；具体时间、能力和状态须以写作时最新版 Lore 复核。

## 七、写作 Agent 工作流程

### 起草（draft）

读最新 `lore.md`、`lore-maintenance.md`、`worldview.md`、同章既有 Interlude 和前后 Sec。先提取**该时间窗口已确定且实际对外可用的重要型号**，再按能力变化组织行文；不从技术百科倒推新设定。写完进行去防御性精修。

### 审查（audit；默认只读）

逐段标记：①重复免责声明；②叠加模糊词；③无必要“不是 X 而是 Y”；④无事实依据的夸张结论；⑤会被误删的必要状态/技术边界；⑥与 Lore 或前后故事时间冲突。对每项提供精确句段、问题和最小修改方案。**未证实的风险标为待核实，不当作确定错误。**

### 精修（polish）

默认**只改防御性句子及相邻衔接**，保持发布日期、模型型号、正式/预览状态、信息量、文风和段落逻辑。删句后重读上下文，防止丢失必要条件。未经要求不改正文其他 Sec、Lore、人物设定或时间线。

### 结构调整（restructure）

仅当用户明确要求，或段落严重变成逐条型号清单时，按技术演进与对照重新组织材料。重新排序不得打乱故事内的时间因果，不能增加未批准的事实。

### 终检问题

- 第一段是否直接告知这一时期发生的技术变化？
- 每个型号是否有具体能力、实际开放状态或重要产品变化，而非空泛形容词？
- 同一条边界是否反复出现？删掉后会否导致实质性误解？
- 是否存在无来源的架构、分数、价格、行业评价或未来预测？
- 是否误把模型能力和网页端 / CLI Agent 系统能力写成同一件事？
- 是否把真实 Preview、受邀与公开渠道混淆？
- 如果删掉结尾的“当然、不过、并不意味着”段，文章是否反而更清楚？

**交付原则：先让读者看见具体进展，再用必要事实限定其意义。写得直接，不写得武断。**
