# 《总谱》后续剧情方向与技术叙事原则

> **定位**：第一学期后续的长期规划与候选故事库；不替代 `lore.md` 的技术时间线、`worldview.md` 的人物事实或 `beats.md` 的第一学期具体节拍。不代表相关章节已经完成。除明确标注已讨论确定的方向外，具体细节仍需逐步讨论。

## 一、成长机制（已确认方向）

孙博逐渐发现，前沿 AI 的能力远超自己接触的课程和初级代码难度。他从遇到作业问题才咨询 AI，转向主动高频交流、检索、让 Agent 尝试解决真实问题。发展差距应通过连续的兴趣驱动短故事表现：更快验证想法、踏入陌生技术、获得外部反馈，再积累下一次尝试的经验。其他同龄人也使用 AI；差距来自探索频率、实际参与和经验累积，不提前决定最终成就。

区分**自身独立掌握的知识**与**能够借助 AI 调动的工作能力**。能力可能远超理解深度，成长也可能不均衡；以行动和结果写，不要抽象宣告天赋或直接灌输技术理论。

## 二、2022 年寒假 Minecraft 开源贡献（课设完成之后）

### 已确认的故事链

1. 孙博结束期末迷宫课设后，寒假玩 Minecraft 大型整合包，遭遇其中某个**大型、GitHub 开源 Mod** 的真实兼容性故障。具体 Mod 名称、问题类型与技术根因待调研设计；整合包与 Mod 代码仓库概念应分开。
2. 他从游戏玩家立场求助 Norbert 与 Kybernetes，逐步提供日志、版本、复现现象。Agent 调研发现源码公开托管在 GitHub，并指导他第一次真正使用 `git clone` 将大型 Java 项目拉到本地。他此前可能见过 GitHub 下载页，但不知道版本控制与协作流程。
3. Kybernetes 分析源码、构建系统与兼容逻辑，协助修改并在本地构建；孙博安装修复后的 Mod，实际进入游戏测试，确认自己的问题得到解决。对 Java、Gradle 等均属初次实战，不要求先学会全部实现。
4. 他主动追问 Agent：**怎么让原项目的维护者或 Contributors 知道自己的修复？** Agent 解释 Issue、Pull Request 及贡献流程，先搜索已有 Issue。其他玩家也提过类似问题，但信息零散；孙博在 Agent 帮助下准备清晰准确的版本信息、复现步骤、预期/实际行为、日志和关联报告，自己核实事实后**第一次提交高质量 Issue**。
5. 维护者或核心 Contributors 发现该报告比既有相似报告更具可复现性和排查价值，予以关注、关联重复报告，并进一步注意到他准备提交的修复。通过维护者实际行动、评论来体现重视，不由旁白宣布他压倒所有贡献者。
6. 在 Agent 指导下，孙博第一次体验 **Fork、分支、Commit、Push、PR** 等操作。第一次 PR 并非一步过关：项目的 lint / 风格检查、pre-commit 或同类提交前检查、Gradle 构建、GitHub Actions CI 与维护者 Code Review 逐步形成反馈；项目究竟采用哪些实际门禁，须基于具体技术原型核定，不能机械把所有工具都视为必须。
7. 孙博把 CI 日志与维护者评论交给 Agent，多轮修改后在同一 PR 分支继续推送，重新运行本地检查并等待 CI 重新通过；学会公共仓库的规范、变更范围及回归验证与“本地能玩”不是一回事。
8. **首次 PR 最终合并**。下一版 Release Notes 公告修复，并公开感谢孙博作为外部贡献者、引用其 Issue / PR；可出现在 Contributors 记录中。不要自动将其升级为仓库 Collaborator、维护者或有写权限的成员；“co-contributor”不作为凭空新增的正式头衔。

### 叙事抓手

- 所有 Git/GitHub 概念与操作都是为眼前问题服务的**第一次**：Clone 是要获取源码，Commit 是记录本地改动，Push 是上传分支，PR 是请求上游接纳修复，CI 是因为提交后出现了真实检查反馈。不要写成命令教学流水账。
- 初期的 Agent 提示很随意、依赖直接操作；随着反馈逐渐开始要求读取 CONTRIBUTING 文档、先做检查、控制改动范围。知识来自实际问题。
- Issue 质量优秀的前提是日志和复现记录真实、经过孙博确认；不是模型编造专业术语。
- 作为章节收束，官方新版本修复了之前的故障、Release Notes 公开致谢，孙博第一次体验到自己帮助陌生玩家改进软件。

### 待讨论

项目原型与兼容性故障、许可证与可构建性、CI 工具和贡献规范、Issue 与 PR 的确切先后/维护者反馈、合并耗时、是否公开说明 AI 使用等。不得提前虚构具体仓库、真实 Issue 编号或 PR 数据。

## 三、青年教师关系线（已确认起点，未来发展待定）

计算机学院年轻教师，授课是职业考核与职称发展的一部分，但教学认真且有热情；科研中较早拥抱 Vibe Coding、AI Agent/Harness，熟悉其工程能力。他在 2022 年 1 月课设验收时从 GUI 作品、源码风格、项目结构、学生回答等综合推测 Agent 深度参与，在公开场合不点破，不强逼解释课外实现。**教师不是通过代码风格神奇鉴定了具体产品。**

老师对孙博的兴趣不等于认定天才或立即招募科研人员；他提出课下单独聊聊，先建立可能的师生联系。其姓名、研究方向、邀请是否实现、下一次互动及长期作用都不预设。

## 四、未来技术与行业 Interlude 的创作原则

- 故事时间超出现实已验证技术后，可以虚构新的实现与技术突破；重点保证**产业、研发、工具能力与后果之间的因果连续、自洽**。允许理论目前无法完整解释的未来能力，不用强迫每次突破都有现成论文背书，也不把“无法解释”写成魔法。
- AGI、AI 参与 AI 研发以及 RSI（递归自我改进）可成为未来演进路线，但**尚未锁定其出现日期、具体机制、发展速度或结果**。AI 研发反馈循环可能加速模型迭代，也要在叙事中呈现算力、验证、资源等实际条件及其变化。
- 模型迭代可以越来越快；并非每次更新都值得一篇 Interlude。行业篇记录重要模型发布、可观察能力与开放状态，人物篇用有钩子的真实任务承接能力变化；不强行让孙博体验每家产品。
- 两段待创作 Interlude：**2021 年 9 月**建立开篇行业格局；**2022 年 1 月前后**表现 Epsilon 与同期技术竞争。其他厂商 12 月至 1 月的迭代仍待讨论，不得填充虚构发布。
- 新 Interlude 写作先依据最新 `lore.md` 和 `interlude-anti-defensive-writing.md`，现实对标只作为作者校准，不在架空新闻里直接出现真实模型名称。
