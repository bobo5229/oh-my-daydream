# 第四章｜一根不肯工作的管道

回家后的头两天，我几乎没碰代码。期末考完，闹钟一关，我先补了两觉，随后才打开收藏夹里那个惦记很久的《方块纪元》科技整合包。

《方块纪元》英文叫 Blockscape，是款运营多年的方块沙盒游戏。我从中学就玩，原版里挖矿、合成、盖房子早不新鲜了；让我每隔一阵子又装回来玩的，是社区那些五花八门的 Mod。眼前这个整合包足足塞了几十个扩展，里面有两款尤其对我胃口：Kinetica 的齿轮、动力轴和传送带能搭出一整条看得见的流水线；Nexalogic 则有工业加工机、分类器和物流管道，可以把东西从这头送到那头。

我想给自己的矿场弄条自动加工线：矿石从箱子出来，经 Kinetica 的漏斗和传送带进入 Nexalogic 管道，再送往加工机。省得我来回背包搬东西。

一个下午过去，齿轮装反两回，动力轴也接错一次。最后拉下控制杆，传送带终于动起来，矿石沿着木架子一格格向前走，钻进漏斗，另一端的机器亮起工作灯。

我端着水杯在电脑前看了半天。虽然折腾了几个小时，但看着自己搭出来的东西自动运转，还挺过瘾。

第二天重新进存档，机器却不干活了。

齿轮照转，矿石照样送到漏斗口，偏偏进不了物流管道。加工机电力正常，背后储物箱也有空位。我先以为昨晚把什么方向设置弄乱了，检查过滤器，重新放矿石，折腾好一阵子，还是不动。

最后烦得不行，我敲掉连接处的那根 Nexalogic 管道，重新放了一根。

矿石立即流了进去。

我松了口气。可晚饭后再次加载存档，管道又不动了。保存退出、重进，坏；敲掉重放，好；再重进，又坏。

“怎么跟我上次迷宫读档差不多？”我对着屏幕嘀咕。都是退出前好好的，回来就不对劲。

我先去中文论坛搜。有人说可能是整合包版本冲突，有人让更新加载器，还有人干脆建议重装。存档是我辛辛苦苦搭的，我不想拿它冒险。于是先做了备份，再把版本号、日志和表现发给 Norbert，问这究竟是哪边的毛病。

Norbert 没立刻判定谁有问题，而是建议排除无关设备。我另开了创造模式测试世界，只放一只 Kinetica 漏斗、一段 Nexalogic 管道和一台加工机。首次放置能用；退出重进失效；重新放管道恢复。换成 Nexalogic 自己的输入装置，反复重进却没事。

我把步骤记进文本文件，甚至录了段短视频。原来的大工厂先放在一旁，我现在就想弄清楚，为什么这一根管道非得每回拆了重装。

后来 Norbert 查到了 Nexalogic 的 GitHub 源码仓库。我原先只知道 GitHub 能下载代码，看到页面上那么多文件、提交记录和问题讨论，才第一次意识到自己游戏里装的一个 Mod 背后竟然是这么大一个项目。

“能让 Kybernetes 直接看看吗？”我问。

我把版本、复现步骤和仓库地址交给终端里的 Kybernetes。它先建议把公开仓库 Clone 到本地，并解释 `git clone` 能下载源码和历史记录，方便后面提交修改。

“那不就跟下载压缩包一样？”我问。它说不完全一样，又解释了一遍分支和提交历史。我没记住多少，只确认了操作。

工程拉下来后，文件列表长得看不见底。到处是 `.java`，旁边还有 `gradlew` 和一堆构建配置。我点开一个类，看了满屏的泛型和方法名，读不了几行就退出来。

Kybernetes 倒是开始认真检查：它搜索物品接口和管道连接的处理代码，对比首次放置、区块加载和邻居变化时会走的逻辑。第一次构建还因为本机开发环境不匹配失败了。它从项目文件里确认 Java 版本，改用仓库自带的 Gradle Wrapper 继续准备依赖。我等下载等得有点烦，中途还去刷了会儿视频。

最终，它给出的判断很具体：管道会缓存邻接设备的物品接口；世界卸载后，那份接口对象可能已经失效，但重新加载时没有在这个组合下及时刷新。拆了再放会触发完整的邻居检查，所以又能用。

我对 Java 和这些接口几乎一窍不通，可这个解释和我的复现现象能对上。

Kybernetes 改了连接刷新逻辑，按仓库构建出供本地测试的 Mod 包。我备份测试世界，把 Nexalogic 换成修复版，亲自进游戏试。第一次正常，退出重进正常，再试仍然正常。回到大工厂存档，矿石也能持续进入加工机。

几小时前还折腾得我想卸载的东西，现在总算能玩了。

本来事情到这里就该结束。我却想起搜索时看到那些“管道偶尔不抽物品”的求助帖，便问 Kybernetes：“我这个已经修好了，怎么让原来做 Mod 的人也知道？其他玩家总不能一直拆管道吧？”

它建议先查仓库已有 Issue，再根据贡献规范报告可复现的问题。我第一次认真点开 Issues 列表，搜了“pipe”“reload”和两个 Mod 的名字。已经有人报告相似现象，但有的没写版本，有的只留一句“我也这样”，还有的怀疑错了对象。

Kybernetes 帮我起草了一份 Issue。初稿看上去十分专业，却把一条我没亲自测试过的猜测写成了确定结果。我赶紧删掉，按记录逐项核实，只保留确实做过的操作：游戏与加载器版本、两个 Mod 版本、四个设备组成的最小场景、预期和实际行为、重进世界失效、重放管道恢复。我附上截取的日志和短视频，也说明本地修改能解决我的问题，但没有声称所有环境都验证过。

点击 Submit new issue，我居然比交学校课设时还紧张一点。老师认识我，维护者却不知道我是谁；如果我写错一步，别人照着折腾半天也复现不出来。

晚上没回音。我隔一阵子就刷新一下页面，第二天上午还是什么都没有，索性关掉浏览器去玩游戏。反正自己那份已经修好了，别人有没有时间看，也不是我能催出来的。

下午，手机突然弹出一封 GitHub 通知邮件。我点进去，发现维护者先给 Issue 加了兼容性标签，又把两条零散的旧报告关联过来。他说按照我列的版本和步骤已经复现，尤其是“重放管道恢复、重新载入再失效”这一点，帮他们缩小了排查范围。

下面还有一句：“你提到有本地修复。如果愿意，可以开个 PR，我们一起看看。”

我把那条英文回复来回读了两遍，又点开关联的旧报告。之前在那里留言说“不知道怎么解决”的玩家，忽然不再只是搜索结果里几个陌生的用户名了。

我回了一句感谢，接着就卡住了。

PR 是什么？

Kybernetes 一边指导我操作，一边解释 Fork、分支、Commit、Push 和 Pull Request。我听到一半就有些乱，干脆让它每次只告诉我眼下要做什么。

先读 CONTRIBUTING，再在网页里 Fork 仓库，建立专门用于修复的分支。Agent 检查工作区时发现构建目录里多出不少文件，我差点以为它们也得一起上传。它让我查看变更列表，把这些本地产物排除，只留下需要提交的源码和测试。

到了 Commit 那一步，我又问：“这个提交是发给维护者了吗？”

它说还没有，Commit 只是把修改记录在本地，Push 以后才会出现在自己的远端分支里。等我看到 GitHub 页面上的分支确实更新了，才继续填写 PR 的标题、问题链接和测试说明。

创建之前，我专门把说明又读了一遍，没有把“本地成功”写成“所有环境都没问题”。点下按钮后，一个陌生的界面出现了，我自己的 GitHub 用户名列在贡献讨论里，后面还跟着那条 Issue 的链接。

我忍不住截了张图，却没敢马上关页面，总觉得还有什么手续没办完。

可高兴没多久，检查列表就冒出一个红叉。我点开日志，屏幕上几百行输出看得头疼，翻了半天才找到格式检查报错，和自己在游戏里遇到的毛病根本不是一回事。

随后维护者的 Code Review 也来了。评论没有否定故障分析，反而先确认了修复方向有用；但他指出当前实现可能在每次传输尝试时重新查询邻接接口。一条管道没什么，服务器里若有成千上万根管道同时工作，这些额外查询就可能拖慢游戏。他在一处方法旁留下了具体建议：连接失效时刷新、邻居变化时刷新，区块重新加载后也要正确恢复，但不要无条件在热路径上反复检查。

我盯着那段评论，刚才截屏时那股高兴劲儿消了不少。自己的工厂已经运转好几天，怎么到别人这里还不合格？

“我这里不是修好了么？”我把评论复制给 Kybernetes，口气也有些冲。

它没有替我反驳，而是举了个简单的例子：我家只有十几根物流管，维护者要顾及的是数千根管道同时更新的多人服务器。第一版修复是为了保证能用，给了每次传输一个重新检查的机会；那不等于这种代价能被所有玩家接受。

我又把那段话看了一遍，才问：“就是说不能每次都重新找邻居，要等该刷新的时候才刷新？”

它说方向是这样，但究竟什么时候刷新，还得符合现有代码处理区块和邻接设备的方式。我想了想，在 PR 下面回复维护者：我会按建议调整缓存更新，并补充测试。第一次写这种公开回复，我删掉了两句没必要的解释，只留下准备修改的内容。

我让 Agent 先阅读项目里相邻的缓存失效逻辑和贡献规范，不要为了修这一个 Bug 另造一套系统。第二版改动少了很多：尽量复用已有的刷新入口，只在接口失效、区块恢复或邻居变化时更新，并加上世界重新载入的测试。

我又在创造模式里搭起那套只有几台设备的小机器，保存、退出、重进，一切正常。正准备把结果回复过去时，我顺手敲掉了紧贴管道的漏斗，却发现连接外观还留在原位。重新放回去再拆一次，问题偶尔会出现。

“这算不算新的 Bug？”我问。

Kybernetes 对照修改前后的处理流程，发现邻居变化时有一条失效通知没有覆盖到。它又做了局部调整。我重复拆装、重新加载和连续传输的测试，确认这两种情况下都正常，才把结果补进 PR。

修改仍推到原来的分支里，GitHub 上的同一个 PR 自动多出了新的 Commit，检查也重新开始。我原先以为每改一次都得重新开一个 PR，折腾这一轮才明白不用。

不久 CI 又红了。这回不是格式问题，是新增测试偶尔失败。维护者指出测试假定了一个固定的区块加载顺序，而实际运行中邻接设备可能先后初始化。Agent 帮我读懂评论，我们调整测试，让它只验证最终需要满足的连接行为，不依赖某个特定顺序；我也重新确认这个测试仍能抓住最初的重载失效问题。

之后我不再只盯着红叉和绿勾。每次提交前，我都先问清楚动了哪些文件、会影响什么场景，再把关键步骤自己跑一遍。Java 的实现我依旧看不懂大半，但至少不想把一份完全没试过的修改交给别人。

最后一次检查全绿时，PR 并没有立刻合并。我看见维护者留下了批准意见，说这个版本可以接受。我回了句感谢，过了一会儿页面状态才变成 Merged。

我在屏幕前愣了一会儿，把页面往上翻，看到最早那条 Issue、自己写得不太顺的第一条回复，还有维护者指出性能问题时留下的评论。短短一个页面，竟已经来回改了这么多次。我截了张图，发给一个平时也玩科技整合包的朋友。他先回了一串问号，随后问：“你给这个 Mod 修 Bug 了？”

“算是吧。”我想了半天才打出这三个字。

又过了一段时间，Nexalogic 发布了包含修复的新版本。Release Notes 的兼容性条目里链接了 Issue 和 PR，并按惯例感谢外部贡献者，后面就是我的 GitHub 用户名。维护者没有因此给我仓库写权限，项目里每天仍有新的问题报告。我只是第一次在这种地方看见了自己的名字。

我把测试世界里那份本地构建的 Mod 包换成官方发布版，重新进入《方块纪元》。传送带继续转，矿石穿过漏斗，顺着物流管道进入加工机。我把游戏人物停在旁边，等了一整批矿石加工完，又保存退出、重新进了一次。

仍然正常。

以前我在论坛里下载别人做的补丁，通常只会回一句“感谢大佬”。这回看着官方版本里同样运转的机器，才觉得那句感谢后面原来有这么多具体的事情。

我关掉测试世界，回到自己的工厂，在生产线尽头又摆了一台新机器。

寒假还长，先玩再说。
