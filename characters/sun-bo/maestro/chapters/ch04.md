# 第四章｜一根不肯工作的管道

寒假第一周，我几乎没碰任何专业课的东西。大一上学期的期末考刚折腾完，回家的前两天我直接把手机闹钟全关了，每天睡到中午才爬起来。吃了我妈留在锅里的早午饭，我便拉上书房的厚窗帘，按开笔记本电源，迫不及待地打开了收藏夹里吃灰很久的《方块纪元》整合包。

《方块纪元》英文叫 Blockscape，是个运营了快十年的体素沙盒游戏。初中那会儿我就跟着网上的教程玩原版，在地下挖铁矿、拿黑曜石搭传送门早就没了新鲜感；真正能让我隔三岔五重新装回电脑里的，是社区里那些五花八门的科技模组。眼下这个重度整合包里装了六十多个模组，其中有两个最合我的胃口：Kinetica 擅长做机械传动，黄铜齿轮、传动轴和帆布传送带能在地上铺出整套肉眼可见的立体流水线；而 Nexalogic 则走精密工业路线，拥有各色带接口的加工机、物品分类器和青灰色的半透明物流管道。

我想在自己的主矿区旁边搞一条全自动的矿石处理流水线：粗铁矿从地下的储物箱顶出来，经由 Kinetica 的机械漏斗倒在传送带上，送进 Nexalogic 的抽取引导管道，最后分流喂进三台联排的高温电炉。这样我就用不着每隔半小时就背着一身沉甸甸的矿石在矿坑和熔炉之间来回跑。

整整一个下午，房间里回荡着键盘敲击和齿轮咬合的声响。传动轴的角度接错了一次，大齿轮的转速配比又搞反了两回，直到把最后一根转接轴卡进木质轴承座，我才扳下铜制的控制杆。齿轮系伴随着一阵沉闷的机械轰鸣飞快旋转起来，传送带平稳移动，深灰色的铁矿石沿着木架子一格格向前滑行，准确落进漏斗，管道内壁泛起淡淡的微光，另一端的电炉随即亮起了暗红色的工作灯。

我端着手边的半杯凉白开，靠在椅背上足足看了好几分钟。风扇在机器底下低低地转着，看着传送带和管道把散乱的原材料源源不断送进机器，那种看着复杂系统自己运转起来的踏实感，比手搓十把钻石镐都要过瘾。

然而第二天下午，等我重新双击载入存档时，整条流水线却悄无声息地停摆了。

齿轮依旧在轰隆隆地转动，传送带也把一兜兜矿石整齐码到了末端的漏斗口，偏偏就在接进 Nexalogic 管道的入口处堵成了一团。加工机里的电力满格，背后的成品箱空空如也。我以为是昨晚关机前误触了管道的方向过滤器，蹲在方块前反复右键查看设置，又把矿石掏出来重新塞进去，整整折腾了十分钟，管道口依然毫无动静。

耐性耗得差不多了，我顺手抄起铁镐，一把敲掉了连接处的那根青灰色管道。

伴随着一声碎裂的脆响，管道化作掉落物掉在脚边。我捡起来重新对准漏斗贴上去。

一瞬间，积压在漏斗里的铁矿石刷地一声顺着管道滑了进去，电炉的排气孔重新冒出青烟。

我吐了口气，以为只是寻常的方块卡顿。可吃完晚饭再次载入游戏，同样的毛病原封不动地又跳了出来：退出前明明跑得好好的，只要重进世界，管道就直接装死；敲掉重新放一遍，立刻恢复正常；再次保存退出、重新进入，再度堵死。

这现象跟期末写迷宫大课设时的读档故障几乎如出一辙——都是关掉前好端端的，重新加载进来就丢了状态。

我跑去模组贴吧和玩家论坛各发了一篇求助帖，写清楚 Kinetica 的漏斗接上 Nexalogic 管道后，重新进入世界就不再输送矿石，还附了几张游戏截图。帖子很快有了回复，可大多没什么用：有人猜是模组冲突，有人让我降级加载器，还有人只丢下一句“重装试试”。倒是有个玩家说他也碰上了，一模一样地重进世界就断，敲掉管道再放又能用。我赶紧追问他怎么解决的。他隔了一会儿回道：“我也不知道，每次上线都重放一遍，烦死了。好像就是前两天更新 CoreLink 之后开始的。”

CoreLink 是整合包里好几个科技模组共用的前置库。我看了一眼启动器的更新记录，里面确实有它，可光凭一句话，我也说不准是不是它惹的祸。后来求助帖被转进一个整合包交流群，陆续又来了些回复，更多是问进展，真正能解决问题的仍然没有。

至少不是我一个人搭错了。我又在帖子里补充了版本信息，但再没人给出可靠的办法。这个存档是我花了整个学期零碎时间一点点搭起来的基地，我不敢拿它去试那些来路不明的重装建议。于是先把整个存档目录打成压缩包备份到桌面，再把游戏版本号、运行日志和复现现象发给网页端的 Norbert，问它到底是哪家模组的机制在打架。

Norbert 的建议很冷静：先别在庞大的主存档里乱动，把无关的齿轮和箱子全部剔除。它注意到我转述的 CoreLink 更新线索，让我在备份后的独立测试环境里比对新旧版本，并确认两个版本都满足当时模组的依赖要求。

我在游戏里新开了一个平坦地形的创造模式测试世界，打开区块边界显示，把 Kinetica 漏斗放在一侧边缘，Nexalogic 管道紧贴着摆在相邻区块，末端接一台加工机。场景里只留下这三样设备和测试用的矿石，方便反复离开加载范围再返回。

测试比想象中麻烦。用整合包更新前的 CoreLink，我保持布局不动，反复保存、重进和走远返回，暂时没复现故障；换回新版，初次放置仍能传输，但十来轮同样的操作里有几次卡死，拆掉管道重放又恢复。若把前端的 Kinetica 漏斗换成 Nexalogic 自带的输入设备，新版 CoreLink 下也一直正常。Norbert 还让我试着从设备附近跑远再回来：当连接两侧的区块发生卸载、重新加载，问题也有机会出现，但并不是每次都中招。

我一度以为自己记错了步骤，只好把每次使用的版本和结果都记下来。最后总算摸出一个规律：新版前置库、两款模组的这组接口连接，以及世界重新加载的时机凑到一起时，故障更容易发生。我不敢说排除了所有可能，只是这些对照结果足够让我继续往下查。Norbert 还让我核对整合包的依赖清单，发现其中有其他模组要求新版 CoreLink；直接降级或许能临时绕开问题，却不适合拿来修我日常玩的整套配置。

我随手切出记事本，把这套复现步骤一条条记下来，顺手用录屏软件录了一段三十秒的操作短视频。原先宏大的工业基地被我暂时抛在了脑后，此时此刻，我只觉得眼前这根莫名其妙的管道格外扎眼。

Norbert 综合我保存的运行日志、版本差异与模组信息，在 GitHub 上找到了 Nexalogic 的公开源码仓库。

在此之前，我对 GitHub 的认知仅限于一个下载开源软件或者找整合包的网页。可当那个黑底白字的仓库页面真正在浏览器里铺开时，密密麻麻的目录树、成百上千次的 Commit 提交记录，以及标签栏里几百条关于漏洞和功能的讨论帖，着实让我愣了一下。我第一次真切意识到，自己天天在游戏里摆弄的一个小道具，背后竟然是一套由真实程序员长期维护的复杂软件工程。

“能让 Kybernetes 直接进去看看到底哪行代码写岔了吗？”我切到终端问了一句。

我把具体的复现步骤、测试日志和 GitHub 仓库的网页地址丢给终端里的 Kybernetes。它扫完说明，建议先用 `git clone` 把公开代码仓库拉到本地。

终端里的进度条飞快滚动，一串串对象被打包下载到本地硬盘。工程展开的一瞬间，文件夹列表长得让人眼晕，目录深处全是以 `.java` 结尾的源文件，根目录下还躺着 `gradlew` 构建脚本与一大堆配置。我试着随手点开一个处理管道逻辑的类，屏幕上密密麻麻全是泛型、事件注解与抽象接口方法，没看超过十行脑门就隐隐作痛。

所幸在终端里跑着的 Kybernetes 不需要我人工去啃语法。它迅速在代码库中检索物品接口与跨模组兼容包，顺着区块加载、方块被破坏以及邻接方块更新这三条事件链路顺藤摸瓜。中间因为我电脑里只配了大一用的 MinGW C 语言环境，缺少 Java 开发套件，第一次调用 Gradle 构建时直接报错退出；Kybernetes 从项目配置确认了需要的 JDK 版本，指导我安装并配置好开发工具，再使用仓库自带的 Gradle Wrapper 下载所需的 Gradle 发行版与项目依赖。

等到终端终于打出就绪提示时，它给出的根因诊断清晰得让我意外：

CoreLink 旧版在设备恢复时会额外发出一次连接更新通知，即使 Nexalogic 的第三方设备接口缓存没有正确处理失效，也常常能被这次通知重新唤醒。新版 CoreLink 去掉了这条不保证存在的冗余恢复通知，但正规的接口失效通知仍然存在。使用方应在失效时清掉旧缓存，并在邻接设备重新可用时重新获取接口。Kinetica 重新加载后仍会提供有效的物品接口，Nexalogic 自己的设备连接也能正常重建；偏偏它处理第三方机械漏斗的旧路径没有可靠清除失效缓存、重新查询邻接接口。遇上特定的区块恢复顺序，管道看着接好了，却无法输入物品。拆掉重放则会触发完整连接检查，暂时恢复。问题因此出在 Nexalogic 对接口生命周期的处理上，而不能简单认定 CoreLink 更新写坏了。

那些接口生命周期的说法我大多听得半懂不懂，但这个因果解释跟我白天反复验证的现象严丝合缝。

Kybernetes 先用了一个直接但粗糙的办法：每次尝试传输前都检查邻接连接状态，并可能重新查询设备接口，绕过原本没有及时刷新的缓存。这能避开我遇到的旧连接问题。它随后在本地调用 Gradle 打包出一个供测试用的 `.jar` 模组安装包。我小心翼翼地把这个自制补丁放进测试整合包的模组目录，再次点开那个只有三台设备的测试世界。

首次放置，矿石顺畅滑行；使用新版 CoreLink，反复退出和重新载入，管道都能继续抽料；换回旧版也没出问题。我又按同样的跨区块布局反复离开再返回，确认先前较容易卡住的步骤没有再出现异常，随后将修复包放进备份过的大存档，积压了半天的流水线终于重新运转，成品铁锭一块块吐进储物箱。至少这些我亲手试过的场景都恢复了正常。

本来折腾到这一步，我自己的游戏已经能正常玩了。我先回到贴吧更新求助帖，说自己借助 AI 找到了一个可在本地复现和修复的方案。先前那个每天重放管道的玩家很快来问：“能不能录个视频看看？”其他人也在追问新旧 CoreLink 到底有什么不同。

我想起自己录过那段三十秒的复现视频。因为故障并非每次重载必现，我也准备在视频中说明重复测试的次数，不把剪出来的一次失败说成必然结果。反正游戏还开着，干脆又补录了旧版正常、新版容易卡住、换上本地修复版恢复的几段画面，把 Kybernetes 排查时的部分终端输出也截了进去。周末花了点时间剪辑、配音，上传到国内视频站 Gulu。标题大意是《科技整合包更新前置库后管道不工作？我用 AI 找了找原因》，标签写上 `#方块纪元`、`#科技整合包`、`#Kinetica`、`#Nexalogic`、`#CoreLink`、`#AI编程` 和 `#Bug修复`。

视频里我没装自己会 Java，只说是 Norbert 帮我梳理现象、Kybernetes 读源码并修改，我负责搭测试场景、对版本、进入游戏确认结果。末尾还特地加了句：目前只是本地实验性修复，没经过 Nexalogic 官方审核，暂时不提供改过的 `.jar` 下载。

视频发出时没多少人看。我把链接贴回贴吧和论坛，后来有人转到整合包交流群，播放量才慢慢涨起来。两三天后，我打开 Gulu 后台，数字已经到了五千多，评论区也热闹了不少。那个和我遇到同样问题的玩家认出了自己的情况，在下面回了句：“原来真能修，我还在每天拆管道。”

最初的评论大多问能不能分享安装包。再往后，有人开始说：“既然源码都改了，UP 不如把代码传 GitHub，让懂的人也看看。”我知道 GitHub 能放代码，但不知道该传整个 Nexalogic 工程，还是只放改动部分，更不确定直接发一个自己修改过的版本是否合适。

又过了一会儿，一位看起来熟悉开源项目的网友回复前面那条评论：“Nexalogic 自己就有官方仓库，别急着另开仓库发布改包。先查有没有类似 Issue，没有就把版本对照和复现步骤提交给维护者。有本地修复的话，后面还能 Fork 原仓库提 PR。”

我盯着这条评论看了几遍。视频本来只是想给贴吧里那些同样被管道折腾的人看，没想到评论区有人指出了另一条路。

我打开 Kybernetes，照着网友的话问：“他们说应该去官方仓库提 Issue，不是直接上传安装包。Issue 到底怎么弄？”

Kybernetes 这才带我回到 Nexalogic 仓库，建议先搜索已有报告，再按项目模板提交真实的复现证据。

我点开仓库顶部的“Issues”标签页，在搜索框里敲下“pipe”、“reload”、CoreLink 以及 Kinetica 的名字。回车按下，列表里确实弹出了七八条类似的抱怨，但里面的内容乱得一塌糊涂：有的帖子只留下一句“管道不工作了求修”，有的连游戏版本都没注明，还有的玩家把矛头指向了显卡驱动。

Kybernetes 很快帮我拟定了一份全英文的 Issue 草稿。乍看过去通篇都是地道的专业术语，可读到中间，我发现它自作主张加上了一句推测“该缺陷可能在所有的第三方机械模组中均存在”。

我想了想，把那句大而化之的假定全部删掉，老老实实对照我本地记事本上的记录逐项核准：明确写出《方块纪元》的游戏版本、模组加载器版本、CoreLink 更新前后的版本、两个模组的具体构建版本，以及那个由三台设备组成的最小复现环境，还列出哪些组合正常、哪些组合容易触发。我附上先前的原始复现片段、运行日志和 Gulu 对照视频链接，末尾老老实实补充了一句说明：本地通过调整失效接口刷新逻辑可以解决问题，但我仅在单机环境做了验证，不确定其他系统表现如何。

按下绿色的“Submit new issue”按钮时，手指悬在触摸板上微微停顿了一下。期末给老师交大课设好歹大家低头不见抬头见，而在一个全英文的大型开源项目里发帖，对面的维护者不仅隔着半个地球，甚至不知道我只是个连 Java 语法都看不全的大一新生。万一我哪一步写得不严谨让人白跑一趟，想想都觉得脸上发烧。

当天晚上没有回音。我合上电脑躺在床上刷手机，每隔半小时就忍不住点开邮箱瞅一眼。第二天上午依然静悄悄的，我自嘲地笑了笑，觉得自己有些自作多情——人家主创团队可能忙着上班上学，哪有空天天盯在网页前守着一个跨模组的小毛病。

转折发生在下午两点多。手机屏幕忽然嗡地震动了一下，通知栏赫然弹出一封来自 GitHub 的系统邮件。

我猛地从椅子上坐直身子，点开邮件里的链接。

一位挂着核心贡献者头像的维护者在我的帖子下留了言。他不仅把我的 Issue 加上了带有紫色色标的 `bug: compatibility` 标签，顺手把前两个语焉不详的旧讨论关联到了我的名下，还在评论里言简意赅地写道：

“按照你给出的最小环境与步骤，我们成功复现了故障。其中 CoreLink 新旧版本对照、重新放置管道暂时恢复的细节，很有助于缩小调查范围。你在帖子里提到手头有一份本地修复？如果有兴趣，欢迎提交一个 Pull Request，我们可以一起审阅。”

我把那两行英文来来回回看了三遍，又顺藤摸瓜点开了那两个被关联进来的旧帖子。我又想起先前在自己求助帖下回复、后来还跑来 Gulu 评论的那个玩家。先前只是我俩反复拆管道，现在至少有维护者照着这套步骤查了。

我心头腾起一股难以言说的兴奋，可手刚搭在键盘上，整个人又卡壳了。

PR 到底是个什么东西？

终端里的 Kybernetes 一边给我解释 Fork、分支、Commit、Push 与 Pull Request 的全套概念，一边指导我执行具体动作。那些关于版本分叉和分支合并的理论听得我脑子发胀，我干脆让它把大道理全收起来：“你就一步步告诉我，我现在该点哪里、敲哪行命令。”

先在浏览器仓库右上角点“Fork”，在我自己的 GitHub 账号下创建原仓库的副本；接着在本地工程里拉出一个专门针对该故障的分支。Agent 在扫描工作区准备提交时，发现刚才本地测试时留下了不少自动生成的配置文件和临时模组包，我本以为只要改动过的东西都得打包上传，Kybernetes 及时止住了我，指导我仔细核对 Git 状态，第一次只暂存修复涉及的两处源码，把多余的构建产物全部剔除干净。

按照格式填好提交信息，在本地执行了 Commit。敲下 `git push` 的瞬间，终端滚动出上传对象的提示。切回自己的 GitHub 页面，一个带有醒目绿色高亮的“Compare & pull request”按钮赫然跳了出来。

我耐着性子把之前在 Issue 里的测试要点又核对了一遍，小心翼翼地把说明文本填进框里，末尾关联上对应的 Issue 编号。点下创建按钮，页面跳转，新建的 PR 页面在屏幕上铺开，我的个人 ID 第一次正式嵌进了开源社区的讨论区里。

我忍不住拿出手机对着屏幕拍了张照片，坐在书桌前傻乐了半天。

然而那股新鲜劲儿还没维持半小时，页面下方的检查列表里就刷出了一个刺眼的红色叉号。

我点开查看详细日志，终端和浏览器里密密麻麻滚过上百行全英文的报错。我原以为是自己的修改把哪块功能改炸了，心跳瞬间快了几拍。等 Agent 把错误信息摘出来，我才发现居然是代码风格检查（Checkstyle）没通过——Kybernetes 在本地格式化时，在一段条件判断语句后面多留下了一个空行，且大括号的换行不符合项目严苛的代码规范。

格式在本地调整好重新推上去，隔天，那位维护者才留下 Code Review 评论。

维护者的语气相当客气，先肯定了这套修复思路确实能解决失效问题，随后在具体的修改行下方留了一条极具分量的批注：

“目前这份补丁在物品抽取的高频路径上增加了反复检查与可能的邻接查询。单机环境下几台机器测试或许感受不明显，但在拥有上千根管道的大型多人服务器中，这种无节制的接口重查会严重拖累服务器的运算刻频率（TPS）。建议通过接口失效通知和已有的邻居变化、区块恢复处理流程来更新缓存，不要在热路径上重复查询。同时补上新旧 CoreLink 组合的回归测试。”

看着那段长长的技术批注，刚才那股沾沾自喜的劲头一下子凉了大半。

“我自己的工厂里跑得顺顺当当，连着玩了三个小时都没掉过帧，怎么一到他们那儿就成了拖累服务器的残次品了？”我把批注复制进终端，敲键盘的声音有些发冲，心里难免带着几分被挑刺的不服气。

Kybernetes 没有顺着我的情绪抱怨，而是极其客观地在终端里给我算了一笔账：

我自己的单机矿区拢共只有不到三十根管道，即使每次传输都增加邻接查询，现代电脑的 CPU 也能轻轻松松抗住；但作为面向大量玩家的模组，多人服务器可能同时运行成千上万根管道。如果每根管道在传输时都重复查询邻接设备，这些额外开销累积起来就可能造成明显的卡顿。

我看着终端里罗列出来的那串数字，手从键盘上缓缓移开。

我不得不承认对方说得在理——我只顾着自己的流水线能不能跑，而维护者还得考虑别人的大型服务器会不会因此变慢。

我深吸了一口气，把刚才草稿框里那些试图自辩的字句通通删掉，老老实实回了一句简短的英文：“谢谢提醒。我之前没考虑到这么多管道一起运行的情况，会按你的建议再改改。”

接下来的两个小时，书房里的空气显得有些胶着。

我让 Kybernetes 先看看项目原来怎么处理连接更新，尽量沿着已有的写法修改，别为了这一根管道另搞出一套复杂东西。第二版的改动比最初精炼了许多：Agent 沿用项目已有的缓存失效入口，在接到有效的接口失效通知、邻居变化或区块恢复时重查连接，不再每次传输都例行扫描。它还新增了覆盖 CoreLink 两种版本行为的回归测试文件；我核对后，将这些文件也提交到原来的 PR 分支。

修改在本地编译完成，我再次把它扔进那个三台设备的创造测试世界。

为了万无一失，我没有像上次那样测两遍就算数。我把矿石塞进去，又掏出来；保存退出，重进；正当一切看似天衣无缝时，我顺手拿起铁镐，敲掉了紧贴着管道的那只机械漏斗。

异样发生了：漏斗明明已经化作掉落物被我捡进了背包，但连接处的管道端头依然固执地伸展着连接管道，模型根本没有缩回断开状态。再次把漏斗放回原位，管道反倒不再抽料了。

“这又是什么鬼毛病？”我抓了抓头发，心里涌上一阵焦躁。

Kybernetes 对照源码的事件链路排查了三分钟，很快找出了漏洞：邻居方块被敲掉的一瞬间，原先代码里的一个空指针保护提前触发了 `return`，导致失效通知漏掉了一环。

它做了针对性的局部修补。我再次在游戏里神经质似地反复拆装了七八遍漏斗，确认不管是重进世界、还是在游戏里当场拆建，管道的连接与吸料都能精准跟上方块的变化，才终于把修改推上了远端分支。

这回我甚至不用重新开帖子，GitHub 的同一个 PR 页面上自动追加了我新提交的 Commit。

本以为这下总该大功告成，没成想二十分钟后，自动化集成测试（CI）居然又亮起了刺眼的红叉。

这回检查的报错更让人头大——新增的自动化测试在模拟世界加载时偶尔出现断言失败。隔了一段时间，维护者又在 PR 里留了言，指出测试用例在初始化时隐式假定了一个固定的方块加载顺序，但在复杂的实际世界生成中，不同方块的加载先后并不保证固定。

看着屏幕上跳出来的报错日志，我靠在椅背上长长吁了一口气。我本以为在游戏里试过那么多遍就差不多了，没想到测试本身还能出问题。看着那几行失败信息，我又把日志发给 Kybernetes。

在 Agent 的帮助下，我们调整了测试断言，不再依赖某个固定加载先后，而是等待相关设备完成初始化后检查最终连接状态，并分别验证新旧 CoreLink 下的行为。

重新提交并推送。过了一阵子，屏幕下方的检查列表终于接二连三地亮起了一长排令人心安的绿色对勾。

绿色对勾全亮的那天深夜，页面并没有立刻合并。我刷新了几次页面，看到那位最初回复我的维护者留下了最后的评论：“Clean and well-tested. LGTM.”紧接着给分支盖上了一个绿色的 Approve 标签。

我回了一句诚恳的“Thank you for your patience and reviews!”，随后伸了个懒腰去洗漱。

等我擦着湿漉漉的头发重新坐回屏幕前时，原本绿色的 Open 药丸图标，已经悄然变成了沉稳尊贵的深紫色：“Merged”。

那行提交记录，被正式合入了项目的主干分支。

我盯着屏幕中央那个紫色的图标看了很久。

把网页往上滑，看着最初自己笨拙发出的第一条复现求助、中间被维护者点名批评性能时的面红耳赤，再到后来连夜抓出新 Bug 重新提交测试的记录……短短一页代码讨论，竟然不知不觉磨合了整整三天。

我截了一张带有紫色 Merged 标记的屏幕截图，随手甩进了平时玩得最好的联机开黑群里。

正在熬夜排位的朋友隔了半分钟才发来一长串问号：“？？？”

紧接着跟了一条语音：“卧槽博哥，这全英文的玩意儿是啥？你给 Nexalogic 官方修 Bug 去了？”

我端着手里的温水喝了一口，在键盘上敲了三个字发过去：“算是吧。”

寒假过去了大半，在快过年的前几天，Nexalogic 官方推向各大模组平台的正式版终于迎来更新。

在游戏启动器的版本更新说明（Release Notes）里，兼容性修复那一栏赫然挂着一段简短的英文公告，末尾带着对应 Issue 和 PR 的超链接，并按照开源惯例写着一行加粗的小字：

“Special thanks to @sunb0 for identifying the capability caching flaw and contributing the patch.”

那是我的 GitHub 账号。过了些时候，我又点进仓库的 Contributors 页面，才在贡献者列表里找到了自己的 GitHub 头像和用户名。点进去能看到这次合并的提交记录。我来回确认了两遍，才相信这不是自己看错了。作为 Contributors 中的一员，并不意味着我有了仓库写权限，更谈不上成了维护者。项目里依然每天都有各地玩家提交新报错。不过能在官方的更新说明里看到自己的名字，我还是忍不住又看了一遍。

我关掉启动器的公告页，先核对新版本支持的游戏版本和 CoreLink 依赖，又备份了一遍存档。确认版本匹配后，才将自制测试包移出模组目录，换上官方正式版。

重新双击点开自己那个庞大的工业基地存档。

阳光从书房的窗帘缝隙里照进来，屏幕上的齿轮依旧在有条不紊地咬合转动，粗铁矿顺着木架子一格格向前滑动，穿过漏斗，没有丝毫停顿地钻进了物流管道，稳稳当当送进另一头的电炉中。

我把游戏人物停在传送带旁，静静看着第一炉铁锭叮当一声掉落进储物箱，随后再次保存、退出、重新载入了一遍。

一切运转如常。

以前在中文互联网上下载别人整合好的资源包，遇到好用的工具，我最多顺手在贴吧或者论坛底下回一句千篇一律的“感谢大佬”。直到自己在这个寒假亲身蹚过了这一趟，看着眼前这条重新畅通无阻的生产线，我才忽然觉得，以前觉得一句“修好了”很简单，现在才知道这中间还有那么多来回修改和检查。

我关掉游戏暂停菜单，操控角色转身回到厂房的一角，在生产线的末端轻快地摆下了一台全新的机器。

寒假还长，先把基地造完再说。
