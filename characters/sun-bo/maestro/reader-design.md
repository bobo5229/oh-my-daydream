# 《总谱》私人网页阅读器｜产品设计共识

> 状态：已确认的产品设计基线（非开发完成说明）  
> 版本：v0.1  
> 整理日期：2026-10-24  
> 范围：`characters/sun-bo/maestro/` 中《总谱》的私人阅读器  
> 维护原则：只记录已讨论并由作者确认的设计决定；推测性实现细节与未定问题明确分开。本文件不定义或修改小说 Canon。

## 1. 产品定位与边界

《总谱》阅读器是一款**只供作者本人使用的现代极简网页阅读器**，兼具长篇小说阅读、AI 行业编年史探索与架空世界资料查阅。

- **正文优先**：让小说正文占据主要视觉空间，工具和辅助信息按需出现。
- **现代、简洁、低干扰**：兼顾精致中文排版与数字出版质感，不做普通博客、传统小说站或复杂管理后台。
- **行业资料可随时查阅**：Interlude 与 Lore 可从侧边抽屉打开，尽可能不打断正文阅读。
- **私人工具**：无需为大众读者、商业化、账号、评论、防剧透或公开发行设计功能。
- **内容与界面分离**：Markdown 原稿继续作为小说内容的权威来源；网页由内容及附加索引生成，新增章节或资源不应要求重复编写页面代码。
- **保护 Canon**：网页项目不得擅自改写剧情、人物设定、企业、模型或技术时间线；小说设定以相应权威内容文件为准。基础模型、Harness、Agent、应用等概念须严格区分。

**工作方式**：先讨论并确定设计，再由 Codex 负责代码开发、文件修改、测试与维护；本文本身不代表已开展实现，也不授权 Codex 静默调整小说内容。

## 2. 信息架构与导航

阅读器包含三个相互关联、体验上各有侧重的内容层：

1. **小说正文**：主要阅读空间；按独立章节自然纵向滚动。
2. **Interlude（行业编年）**：通过故事时间线关联正文，并可独立阅读与浏览。
3. **Lore（世界观档案）**：按人物、企业、基础模型、Harness、技术等实体检索和查阅。

同时提供**独立视觉资料库**，复用小说与资料中的人物形象、场景插图、企业 Logo、SVG 技术图表等资产。

布局分工已确定：

- **左侧**：章节导航抽屉；另外提供可访问的完整章节目录页面。
- **中间**：正文主阅读区。
- **右侧**：Interlude、Lore 等资料抽屉。
- **顶部**：低调的阅读模式快捷入口；章节目录中另有完整的模式选择。

导航与资料查看应尽量保留小说的当前章节和阅读位置。

## 3. 正文阅读体验

### 3.1 排版与视觉基准

| 项目 | 已确认设计 |
| --- | --- |
| 主体风格 | 现代极简、柔和中性色、正文优先 |
| 正文宽度 | 约 720–840px，默认目标约 780px |
| 中文字体方向 | 现代无衬线（如思源黑体 / Noto Sans SC） |
| 默认字号 | 18px |
| 默认行距 | 1.85 倍 |
| 排版设置 | 可调整字号与行距，记住偏好，支持恢复默认 |
| 浅色主题 | 柔和灰白背景与深灰文字 |
| 深色主题 | 深石墨灰背景与柔和浅灰文字 |
| 主题行为 | 默认跟随系统；可手动强制浅色 / 深色并记住选择；可恢复系统跟随 |

颜色参考值：浅色背景 `#F7F7F5`、深色背景 `#202124`。它们只是初始视觉基准，具体对比度、文字色和状态色需在真实界面中校准，不是不可修改的设计令牌。

正文应居中、留白充分，但不强制占满窗口，也不让宽屏上的文字行长无限增长。打开资料抽屉时尽可能减少重新换行和阅读位置漂移。

### 3.2 阅读流程与进度

- **章节独立**：每章是独立页面，自然纵向滚动；末尾通过「上一章／下一章」等入口手动切换，不使用整书无限滚动或电子书式强制分页。
- **自动记录进度**：保存最后阅读章节和章节内较精确的位置，重新打开后恢复到原文字附近。
- **稳定定位**：优先结合稳定内容锚点保存位置，必要时以滚动位置等方式回退；正文编辑或排版变化后不承诺逐字精确恢复。
- **首次访问**：没有阅读记录时展示作品首页，包含标题、封面视觉及开始阅读入口。
- **后续访问**：已有阅读记录时默认直接恢复正文；作品首页仍可从导航进入。
- **分开管理状态**：正文阅读进度与 Interlude、Lore 的临时浏览位置相互独立。
- **本地偏好**：阅读进度、主题和字号／行距偏好可保存在浏览器本地，不需要账号；跨设备同步不是既定需求。

### 3.3 双阅读模式

已确认存在两种内容编排：

- **纯小说模式**：正式阅读顺序只包含小说正文。
- **完整编年模式**：按 YAML 中定义的阅读编排，将 Interlude 纳入正文的正式阅读顺序；「上一篇／下一篇」遵循这套序列。

两种模式**共享同一份正文进度**。在小说正文中切换模式时，当前章节和位置不变，只改变后续阅读顺序；不强制回溯补读未读 Interlude。若从 Interlude 切换回纯小说模式，恢复此前保存的正文位置。

顶部工具栏提供低调的「纯小说／完整编年」快捷切换入口；左侧目录中也提供完整模式选择。切换设置需同步并记住。

**尚未确定**：初次使用时默认启用哪一种阅读模式。此前曾推荐纯小说优先，但作者未就默认值单独作出选择。

## 4. Interlude：时间线与阅读体验

### 4.1 由故事时间驱动的抽屉

- 通过独立 YAML 维护**故事时间阶段**及其与章节、Interlude 的关联。
- 右侧 Interlude 抽屉打开时，自动定位并突出**当前正文对应的故事阶段**。
- 当前阶段默认展开关联的 Interlude；完整时间线保留前后时期，其他时期可手动展开与浏览。
- 不因阅读阶段限制查阅其他时期；本工具不需要防剧透机制。
- 故事时间阶段不强制等同自然月份，可表达跨月阶段与更细的事件时期。

**同步粒度采用混合模式**：一般按章节识别时间；章节内发生明确时间跳跃时，允许通过独立 YAML 和稳定的场景锚点覆盖章节默认阶段。时间变化后抽屉在自动跟随状态下同步。

抽屉有两种状态：

- **自动跟随**：根据小说阅读位置同步当前故事时间。
- **自由浏览**：当作者主动查看其他时期时暂停自动跟随，保留当前浏览位置；通过「返回当前故事时间」重新启用跟随。

自由浏览不能使小说正文跳转或丢失滚动位置。

### 4.2 区分不同的时间含义

至少在概念上区分：

1. **故事时间 / 场景时间**：小说情节发生在何时；
2. **行业事件发生时间**：Interlude 提及的企业、模型或技术事件发生在何时；
3. **Interlude 关联阶段**：从小说某一阶段打开抽屉时，哪些档案值得展示；
4. **阅读编排位置**：完整编年模式下，该篇 Interlude 在何处进入阅读序列。

这些概念不得简单用一个「日期」字段混为一谈；具体 YAML 字段与数据结构待架构设计阶段确定。

### 4.3 Interlude 的展示

- 点击时间线条目后，默认在右侧抽屉阅读完整 Interlude。
- 支持一键展开为独立、宽敞的阅读视图；退出后回到小说原位置。
- 与小说共享整体字体、主题、基础留白与现代极简视觉语言。
- 按需支持行业时间轴、事件卡片、企业 Logo、图片和 SVG 技术图表。
- 普通以文字为主的 Interlude 无需强行插入信息卡片或图表。
- 普通图片自适应抽屉宽度；复杂图表提供完整预览，点击后进入可缩放、可拖动／平移的大图查看器，并可返回原阅读位置。

## 5. Lore：上下文资料库

Lore 右侧抽屉采用**上下文关联 + 完整分类目录 + 全局搜索**：

- 默认呈现与当前章节有关的人物、企业、基础模型、Harness 等实体。
- 可以按类别浏览所有条目，也可以搜索正式名称与别称。
- 实体索引具有稳定 ID、规范名称、别称与明确的实体类别。
- 章节相关实体优先通过扫描 Markdown 自动识别；对误识别、漏识别或特殊关联可使用 YAML 显式修正。
- 自动识别只建立阅读索引，不得创造新设定或修改正文；构建时生成索引是候选优化，并非已经锁定的工程方案。

Lore 条目采用**分层档案**：

1. 在抽屉内先展示名称、类别、摘要、关键属性、形象或 Logo、相关实体。
2. 可继续查看详细资料。
3. 支持展开独立的完整阅读视图。

人物、企业、模型和 Harness 保持一致的设计语言，但可按实体类型展示不同字段。正文阅读位置不应因资料查阅而改变。

## 6. 插图与独立视觉资料库

- **内容内嵌**：场景插图自然穿插在小说相应情节附近；人物立绘用于人物档案；企业 Logo 用于企业资料及相关编年；技术 SVG 用于需要解释关系或演变的档案。
- **克制呈现**：正文插图不应高频打断阅读；通常不超过正文阅读宽度，保留舒适的上下留白，不滥用边框与装饰。
- **高清查看**：点击可放大；复杂图片和图表使用统一的大图缩放和平移体验。
- **集中浏览**：独立视觉资料库按人物、场景、企业 Logo、技术图表等维度汇集和检索视觉资产。
- **资产复用**：同一资源能在正文、Lore、Interlude 和图库中复用，不重复维护多份副本。
- **低侵入关联**：插图位置优先使用 Markdown 原有图片引用或稳定锚点及外部元数据，不为 UI 改写剧情文字。

「隐藏正文插图」曾作为建议提出，但**尚未确认**，不属于本版必做项。

## 7. Markdown、YAML 与内容安全

已确认采用**Markdown 正文 + 可选 YAML 增强**：

- Markdown 仍负责正文、标题、普通图片与基础格式，继续作为小说原稿的权威来源。
- YAML 负责阅读器所需的故事阶段、章节与 Interlude 关联、阅读顺序、实体关联修正等结构化索引。
- Interlude 的复杂时间轴、事件卡片、特殊视觉布局等可通过**可选 YAML**定义，绑定稳定内容锚点。
- SVG / 图片作为独立资产供多个页面复用。
- 没有专属 YAML 视觉配置的 Markdown 文章也必须正常渲染。
- 不依赖容易随编辑变化的**源文件行号**定位内容或场景。
- 内容索引和视觉增强失效时，应降级为可阅读的原始正文，而不是丢失文本。

### 7.1 现有仓库事实与非破坏性兼容要求

仓库现阶段**部分 Interlude 仍嵌入章节 Markdown 的引用块内**，例如：

- `chapters/ch01.md` 开头的 Interlude 01；
- `chapters/ch03.md` 中途的 Interlude 02；
- `chapters/ch05.md` 开头的 Interlude 03。

因此，「Interlude 与正文解耦」目前是**产品展示与数据组织的目标**，不代表这些源文件已经完成物理拆分。

后续开发前必须明确：如何在**不改变原稿**的情况下识别嵌入式 Interlude、在纯小说模式中隐藏相应展示、在完整编年模式中以正确编排显示；对于章节内插入的 Interlude，亦须讨论如何兼顾「独立章节页面」与「正式阅读顺序」。可选方案（安全解析、构建时生成虚拟章节、后续经授权迁移等）**尚未选定**。不能未经授权直接拆分源文件、删除引用块或重写原稿。

关联不清或解析失败时，应报告问题并避免静默截断正文。

### 7.2 权威来源与职责边界

- `lore.md`、`lore-maintenance.md`：AI 架空技术事实、模型／Harness 区分与世界观维护规则。
- `worldview.md`：人物相关事实。
- `chapters/` 下的 Markdown：已完成正文与已写 Interlude 原文。
- `chapters-index.md`：现有章节摘要与时间线检索参考。
- 未来的阅读器 YAML：用于**描述展示与关联**，不能反向篡改上述权威内容。

该文档不发明新的世界观日期、剧情事件、Interlude 编号或技术事实；将来 YAML 示例中的日期与实体必须明确标为示意，除非由权威资料核实。

## 8. 响应式布局

已确认**宽屏并排、空间不足时覆盖**的模式：

- 宽屏时正文与右侧资料抽屉并排，优先保留正文舒适阅读宽度。
- 空间不足时自动退化为右侧覆盖式抽屉，避免把文字栏挤得过窄。
- Interlude 与 Lore 在两种布局下应使用同一套内容组件。
- 抽屉开关、放大视图和模式切换需尽可能保持正文滚动位置稳定。

右侧抽屉**初始宽度约 440px**仅为当前建议的设计起点，并非最终定值；具体响应式断点及宽度上下限待真实布局验证。

## 9. 明确尚未决定的事项

以下问题**不能被 Codex 当作已确认要求**：

- 右侧抽屉是否允许拖动自由调整宽度，或采用固定／预设宽度（问题 27 尚未选择）。
- 左侧目录与右侧资料抽屉是否可以同时展开，以及多抽屉竞争空间时的规则。
- 两种阅读模式首次访问的默认值。
- Interlude 从嵌入式 Markdown 安全识别、虚拟拆分或物理迁移的具体技术方案；章内 Interlude 的详细导航粒度。
- YAML 文件名、目录、最终字段结构、稳定锚点算法、自动识别规则与纠错策略。
- Astro / 原生 HTML CSS JavaScript / TypeScript 等技术栈选择及是否有构建工具。
- 页面动效、精确断点、抽屉宽度上下限、主题完整色板、默认图像大小与插图隐藏功能。
- 搜索的精确交互、图库筛选细节、人物档案完整字段及视觉封面设计。
- 移动端独立交互设计、键盘快捷键、书签等尚未专门确认的扩展项。

作者已明确：**细节留待后续调整，当前优先保存已有设计共识，不立即开始开发**。

## 10. 后续迭代与验收原则

后续由作者与产品／技术顾问逐项明确未定设计，再把锁定结果转化为具体 Codex 任务。首轮实施时至少遵守以下验收边界：

1. 原始 Markdown、Canon 与现有剧情未被阅读器工程擅自修改。
2. 纯小说模式和完整编年模式有清晰、可核验的内容编排规则，且不重复维护原稿。
3. 故事时间线、Interlude、Lore 的关系来自可维护的索引，不依赖硬编码网页。
4. 阅读进度、资料浏览状态和主题排版偏好按约定独立运作。
5. 读者能够在不丢失正文位置的前提下查阅 Interlude、Lore 与视觉资料。
6. 普通 Markdown 即使没有额外视觉增强数据，也能正确显示。

**文档性质**：产品设计共识记录，不是已经完成的 UI、可运行的代码、确定的 YAML Schema 或一次性开发清单。后续新增共识应增量修订本文件，并保留「已确定／待定」边界。
